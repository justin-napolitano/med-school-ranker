# Cards and Mobile Patterns

## Objective

Define how school cards and mobile layouts should work once the UI consumes generated card/profile nodes.

## School Card Anatomy

Each school card should show:

- school name and location;
- Decision Rank and bucket;
- MCAT/GPA fit summary;
- cost/debt summary;
- top positive and negative drivers;
- confidence and missing-data chips;
- profile, compare, shortlist, and hide actions.

## Mobile Behavior

- Keep rank, school name, fit, and action state visible first.
- Collapse secondary details behind clear expand controls.
- Keep filter controls sticky or easy to reopen.
- Avoid large decorative media that pushes data below the fold.
- Preserve source/confidence caveats in compact form.

## Desktop Behavior

- Support card grid and table-adjacent card summaries.
- Allow dense comparison and scanning.
- Keep actions stable across rankings, profiles, compare, and shortlist views.

## Done Criteria

- Cards can work as ranking rows, grid cards, compare summaries, and profile snapshots.
- Mobile users can shortlist, compare, hide, and open profiles without friction.
